## 1. Database connection layer (implemented)

`src/db/postgres.js`:

- **Pooling** — one shared `pg.Pool` per process: `max: 5` (Neon free-tier friendly), `idleTimeoutMillis: 10s`, `connectionTimeoutMillis: 10s`. Neon's PgBouncer pooler endpoint is used via the `-pooler` hostname in `DATABASE_URL`; repositories must avoid named prepared statements (pg's unnamed extended protocol is safe).
- **TLS** — `sslmode=require` in the connection string; pg 8 already enforces `verify-full` semantics for `require`, which Neon's certificates satisfy (verified live). Escape hatch: `PG_ALLOW_SELF_SIGNED=1`.
- **Retry logic** — `initPostgres()` pings `SELECT 1`, applies the idempotent schema, and retries transient boot failures (DNS, TLS, pooler cold start) with exponential backoff (400 ms × 2ⁿ, 5 attempts), then fails with one clear `FATAL:` line (no stack dumps for operators).
- **Error handling** — idle-client pool errors are logged and self-heal; `withTransaction(fn)` commits/rolls back and always releases the client; all queries parameterized (`$1`, `$2`, …) — no string interpolation anywhere.
- **Health** — `pgHealth()` for `/health`; `poolStats()` for observability.
- **Graceful shutdown** — `closePostgres()` in `startServer`'s shutdown path (Phase 2 wiring).

## 2. Data models (implemented at the schema layer)

`src/db/schema.postgres.sql` is a faithful translation of `src/db/schema.sql`:

- `AUTOINCREMENT` → `BIGINT GENERATED BY DEFAULT AS IDENTITY` (auto for the app; explicit ids allowed for the data migration).
- `DATETIME DEFAULT CURRENT_TIMESTAMP` → `TIMESTAMPTZ DEFAULT now()`.
- Seven SQLite `AFTER UPDATE` timestamp triggers → one `set_updated_at()` plpgsql function + `BEFORE UPDATE` triggers (prevents the recursive-trigger pattern).
- All CHECK constraints (`publication_state`, `accessibility_status`, `source_entity_type`, `singleton`), FK cascade semantics, composite-PK join tables, and the five indexes are preserved 1:1.
- `_migrations` table mirrored for the PostgreSQL migration tracker.

**Repository contract (Phase 2 reference pattern — exact SQL already proven in `tests/postgresPipeline.test.js`):**

```js
// before (SQLite, sync)
function listPublished() {
  const db = connectDB();
  return db.prepare("SELECT * FROM skill WHERE publication_state = 'Published' ORDER BY name ASC").all();
}

// after (dialect-neutral, async — identical for SQLite via query())
async function listPublished() {
  const { rows } = await query(
    "SELECT * FROM skill WHERE publication_state = 'Published' ORDER BY name ASC"
  );
  return rows;
}

async function create(data) {
  const { rows } = await query(
    "INSERT INTO skill (name, description, publication_state) VALUES ($1, $2, 'Draft') RETURNING id",
    [data.name, data.description || null]
  );
  return rows[0].id;
}
```

The unified `query(sql, params)` wrapper (implemented in `src/config/database.js`) runs `pgQuery` for PostgreSQL and, for SQLite, translates `$N → ?` and maps `SELECT/RETURNING` statements through `prepare().all()` and mutations through `run()` (rowCount = changes). Repositories are therefore **single-source**, and the driver is chosen at boot: `DB_DRIVER=sqlite` (default until Phase 3) or `DB_DRIVER=postgres`. **Driver note:** the default stays SQLite until the data migration lands, so a developer's `pnpm dev` never silently points at an empty production database; Neon runs are explicit.

**Dialect rule:** repository SQL must be valid on both drivers — no `::` casts (use plain `COUNT(*) AS n` + `Number(row.n)`, since pg returns BIGINT counts as strings), `ON CONFLICT DO NOTHING` instead of `INSERT OR IGNORE`, and no SQLite pragmas in repository code.

**Sequence note:** PostgreSQL identity sequences advance even when a transaction rolls back (the verification probe consumed ids); never assume dense/sequential ids — always read ids from `RETURNING` or from rendered pages (this bit us once during live verification).

## 3. API layer (validated, business rules enforced)

- **Validation** — unchanged and reused: `src/lib/validation.js` (`requireText`, `optionalText`, `requireEnum`, `optionalInt`, `isHttpUrl`) runs in every mutating route before the repository is touched; field errors render inline (400).
- **Business rules** — live in repositories (publication state machine, singleton profile, duplicate-skill names, RESTRICT/409 semantics on claim-linked deletions). The database enforces the invariants a second time (CHECKs, FKs, unique) — defense in depth verified in `tests/postgresPipeline.test.js`.
- **Contracts preserved** — 400 validation / 401 unauth mutation / 403 CSRF / 404 unknown id / 405 method / 409 RESTRICT; POST→303 redirect (PRG).

## 4. Data flow (bidirectional)

- **UI → DB**: every form POST hits a `/manage/*` route → validation → repository → Neon (parameterized) → PRG redirect re-renders from a fresh read. One user action = one database operation; nothing is cached between.
- **DB → UI**: every render reads live from the database. Reflection is immediate on navigation (PRG).
- **Near-real-time (Phase 3, specified)**: server-sent events channel `GET /manage/events` (authenticated SSE). Repositories publish `data-changed {entity, sessionId}` on mutation; the manage layout subscribes via `public/js/live.js` and refreshes affected views — skipping events originating from the same session to avoid double reloads with PRG. ~60 lines total; no new dependencies.

## 5. User experience

- **Validation feedback**: inline `fieldErrors` per input (already implemented and tested).
- **Loading states**: server-rendered pages respond in single-digit ms; forms get `aria-busy` toggles in the Phase 3 enhancement pass.
- **Error messages**: centralized `errorHandler` renders the 4xx/5xx pages; boot failures (connection, port, config) exit with single-line `FATAL:` messages (verified).
- **Data validation feedback**: the CHECK-constraint layer surfaces as 409/400 via repository mapping, never as raw driver errors.

## 6. Admin and user roles (implemented)

`src/middleware/rbac.js`, wired in `app.js` after the session guard:

- `attachPrincipal` stamps `req.principal = { role: 'owner' | 'reader', authenticated }` on every request.
- `requireRole(...roles)` — generic gate (GET → sign-in redirect; write → 401 contract).
- `requireOwner` — the admin gate for `/manage/*` (semantically identical to the existing `requireAuth`).
- **Model**: `reader` = anonymous visitor, read-only on *published* data (GET-only boundary + `publication_state` filters + no public write endpoints). `owner` = the single authenticated administrator, full CRUD. Multi-user accounts are a separate authorized increment (the frozen design has exactly one credential) — the middleware and schema are ready for a `users` table when that happens.

## 7. Testing and validation (partially implemented, pattern proven)

- **Hermetic core suite** — the existing 70-test suite runs on SQLite (`DB_DRIVER=sqlite` forced in `tests/helpers.js`) so CI needs no external service; repository code is identical in both drivers.
- **PostgreSQL pipeline suite** — `tests/postgresPipeline.test.js`, env-gated (`TEST_POSTGRES_URL`, or `DB_DRIVER=postgres` + `DATABASE_URL`): boots the real pool, verifies singleton/UNIQUE, trigger-maintained `updated_at`, cascade semantics, and CHECK constraints. **Currently passing 4/4 against the Neon production branch.**
- **Connection verification** — `node scripts/verify-postgres.js`: retry boot, schema apply, CRUD roundtrip inside a rolled-back transaction (zero residue), pool stats. **Currently passing against Neon (PostgreSQL 18.6).**
- **Phase 4 UI→DB tests** — after cutover, supertest flows run against a throwaway Neon *branch* (`neon branches create` / branch URL per run, dropped after) or a CI `services: postgres` container; the same content/publication suites gain a Postgres matrix lane.
