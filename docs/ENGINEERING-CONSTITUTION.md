# ENGINEERING CONSTITUTION

This document establishes the engineering principles and controls for the Portfolio System project.

## Principles

1. Evidence before claims: Never claim something exists or is true without verifying it through inspection, testing, or reliable documentation.
2. Inspect before modifying: Always examine the current state of files, configuration, and environment before making changes.
3. Never fabricate project state: Do not invent or assume the existence of files, features, or configurations that have not been verified.
4. Never claim completion without verification: A task is complete only after empirical verification that it meets the requirements.
5. Requirements govern implementation: Implementation must strictly follow the approved requirements; no features may be added without requirement justification.
6. Architecture governs module boundaries: Module design and interactions must conform to the approved system architecture.
7. Security is considered during design: Security threats and mitigations must be addressed during the design phase, not added only at the end.
8. Accessibility is part of product quality: Accessibility requirements must be integrated into the design and implementation process.
9. Testing is part of implementation: Verification through testing must accompany implementation; no feature is considered complete without tests.
10. Documentation must remain synchronized: Important decisions, architecture, and requirements must be documented and kept up to date.
11. Unknown information remains explicitly UNKNOWN: When information cannot be verified, it must be stated as UNKNOWN, not assumed.
12. Failed commands/tools must be reported honestly: If a command fails or a tool cannot be used, report the failure accurately.
13. AI-generated code must be reviewed and verified: Any code generated by AI tools must be reviewed by a human engineer for correctness and security.
14. Secrets must never be committed: No passwords, API keys, or other secrets may be committed to version control.
15. Dependencies must have a justified purpose: Every external dependency must be documented with a clear justification for its inclusion.
16. Complexity requires a reason: Added complexity must be justified by corresponding benefits or requirements.
17. Prefer the simplest architecture: Choose the simplest architecture that satisfies the verified requirements.
18. Destructive operations require explicit authorization: Operations that can delete or modify data require explicit approval before execution.
19. A module is complete only after empirical verification: A module is considered complete only after it has been tested and verified to work as specified.
20. The coding agent executes approved engineering decisions: The implementation agent follows approved decisions and does not redefine them silently.

## Compliance

All project participants must adhere to these principles. Violations must be reported and addressed promptly.
