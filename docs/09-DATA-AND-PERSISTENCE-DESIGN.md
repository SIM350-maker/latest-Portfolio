## 4. Persistence Objectives
- Persist all domain data required for functional requirements (P0, P1). 
- Preserve traceable relationships (Claim‑Evidence‑Artifact) and states.
- Separate content from presentation and enforce access control.
- Provide clear identifiers and constraints to guarantee data integrity.
- Design for SQLite, but remain agnostic to implementation details.

## 13. Content and Publication Persistence
- DECISION: Publication State has exactly ONE authoritative stored representation: a publication_state column on each content-managed entity — Professional Identity, Project, Skill, and Claim.
- EVIDENCE: the domain model defines these entities as content items ("Content (Professional Identity, Project, Skill, Claim, etc.) has a lifecycle") and gives each content item a Publication State (1:1). No authoritative document mandates a separate Content wrapper table.
- The former Content wrapper table (content_type discriminator with its own publication_state) is removed; it duplicated the authoritative state without a synchronization invariant.
- Content is therefore the publication-managed role of those four entities, not a separately persisted wrapper table.
- Evidence and Artifact are NOT content-managed and carry no publication_state; their public visibility is derived from the publication state of the content they support (architecture 7.4: evidence metadata is exposed in the Public Evidence System when the associated content is published).
- Lifecycle timestamps (created_at, updated_at) are stored on each entity.

## 14. Relationship and Cardinality Model
- Professional Identity ↔ Skill: 1:N (one identity can have many skills, each skill belongs to one identity).
- Professional Identity ↔ Project: 1:N.
- Professional Identity ↔ Claim: 1:N.
- Project ↔ Skill: N:N via ProjectSkill.
- Project ↔ Claim: 1:N.
- Claim → Evidence: 1:N (one claim can have many evidence).
- Evidence → Artifact: many‑to‑one (each evidence references one artifact.)
- Artifact → Evidence: 1:N.
- Content: a publication-managed role of Professional Identity, Project, Skill, and Claim — each such entity IS a content item; the domain model defines no universal Content wrapper, so no separate content-record relationship is persisted (see Section 13).

## 15. Identifier Strategy
- Surrogate integer or autoincrement IDs for entities.  
- For public facing URLs, slugs derived from titles may be stored as optional unique fields for readability only.

## 16. Integrity Constraints
- Foreign keys enforced at the persistence layer (SQLite PRAGMA foreign_keys = ON).
- Deletion rule: ON DELETE RESTRICT is the default for all relationships, with exactly ONE explicit exception — no relationship is governed by both RESTRICT and CASCADE.
- Explicit exception: Claim → Evidence uses ON DELETE CASCADE (see Section 20).
- Unique constraints on unique business keys (e.g., Artifact reference).  
- ENUM validation on state attributes to enforce defined values.
- Every Evidence references exactly one Claim and exactly one Artifact (Claim → Evidence → Artifact semantics preserved).
- Non‑null constraints on mandatory fields.

## 17. State Persistence
- Publication State: enum ('Draft', 'Published', 'Unpublished'). Stored per entity.
- Accessibility: enum ('Public', 'Restricted', 'Redacted', 'Unavailable').
- Verification Result: enum ('Verified', 'Partially Verified', 'Not Verified', 'Cannot Verify').

## 18. Security and Privacy Persistence
- No authentication credentials are persisted in this design.  
- Sensitive contact information stays within the Professional Identity entity but is only served to authenticated users.
- Private publication states are enforced by application logic; persistence does not expose state changes.

## 19. Stored vs Derived Data
- contact_info may be stored or derived from an external identity service; here we opt to store it.
- Derived fields such as URLs for artifacts are stored as reference strings; the actual content is external.
- Presentation‑only flags (e.g., visibility) are not persisted; derived at runtime.

## 20. Deletion and Lifecycle Rules
- Soft delete is not introduced; hard delete is used under explicit, non-overlapping rules.
- Claim → Evidence: ON DELETE CASCADE. Claim deletion cascades only to its Evidence records; referenced Artifacts remain independent and unaffected.
- Artifact → Evidence: ON DELETE RESTRICT. An Artifact cannot be deleted while Evidence references it; referencing Evidence must be removed first (explicit DeleteEvidence command, or Claim deletion per the rule above).
- Project → Claim: ON DELETE RESTRICT. A Project cannot be deleted while its Claims exist; Claims are deleted explicitly via the separate DeleteClaim command (application design, Section 8), which then cascades to their Evidence. Project deletion never implicitly destroys Claims, Evidence, or Artifacts.
- Project → Evidence: no direct relationship; Evidence is reachable only through Claims (Project → Claim → Evidence). Artifacts are never deleted as a side effect of Project or Claim deletion.
- Professional Identity and Skill deletion follow the RESTRICT default; referencing content must be deleted or reassociated explicitly first.
- Unpublish toggles publication_state to 'Unpublished'; the record remains.
- Archive is a deferred decision (Section 26).

## 21. Module Persistence Responsibilities
- Content Management module owns CRUD and lifecycle tables.  
- Public Presentation module reads from persisted tables; no write operations.  
- Evidence Store module owns Evidence and Artifact tables.  
- Security module has no persistence beyond user session (handled elsewhere).

## 22. SQLite Design Considerations
- Use INTEGER PRIMARY KEY AUTOINCREMENT for surrogate keys.
- Enforce foreign key constraints by setting PRAGMA foreign_keys=ON.
- Large text fields (e.g., description) use TEXT type.
- No external extension modules needed for enums; implement as CHECK constraints.
- Schema designed to fit SQLite’s limited ALTER capabilities.

## 23. Query and Access Patterns
- Read heavy: public portfolio pages.  
- Joins: Project→Claim→Evidence→Artifact.
- Index on foreign keys for join performance.
- Frequent lookups: by slug or ID for public pages.
- Write heavy: content management during draft updates.

## 24. Performance Considerations
- Use simple joins; avoid deep nested queries.  
- Caching at application layer (deferred).
- Avoid storing binary artifacts; rely on external URLs.

## 25. Backup and Recovery Considerations
- SQLite file can be checkpointed and backed up; schedule file copy.
- Ensure transaction integrity; use WAL mode for reliability.
- Recovery via file restore.

## 26. Deferred Decisions
- Whether to split tables for Skill‑Claims, Project‑Claims.  
- Whether to denormalize Artifact reference for faster lookup.
- Whether to introduce computed columns for full URLs.
- Whether to store soft‑delete flags.
- Whether to store audit trails beyond timestamps.

## 27. Risks
- Artifact URL changes could break references; mitigate via manual update or visibility controls.
- Deleting evidence may orphan claims if cascade not configured.
- SQLite file corruption in extreme fault conditions.
- Potential performance hit on JOIN-heavy public pages.
