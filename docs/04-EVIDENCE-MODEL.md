## Evidence Sources
- Source code repositories (e.g., GitHub, GitLab)
- Live deployments (URLs to running systems)
- Architecture diagrams (e.g., C4, UML, cloud architecture)
- API documentation (e.g., OpenAPI/Swagger, Postman collections)
- Test reports (unit, integration, end-to-end, performance)
- Technical documentation (design docs, decision records, runbooks)
- Demonstrations (recorded walkthroughs, screenshots with explanations)
- Performance metrics (benchmark results, monitoring dashboards)
- Certificates and credentials (completed courses, certifications)
- Recommendation letters and endorsements
- Engineering blogs or technical articles authored by the engineer
- Database schemas and migration scripts
- Infrastructure-as-code templates (Terraform, CloudFormation, etc.)
- Security audit reports
- Accessibility audit reports

## Evidence Collection Methods
- Direct linking to publicly accessible resources (repositories, live sites)
- Embedding or attaching files (PDFs, images, documents) with proper context
- Creating summary evidence pages that synthesize multiple sources
- Using version control tags/releases to pinpoint specific evidence versions
- Automated collection from CI/CD pipelines (build artifacts, test reports)
- Manual curation by the engineer with explanations of relevance

## Evidence Storage and Retrieval
- Evidence shall be stored in a manner that ensures longevity and accessibility (preferring durable, standardized formats).
- The system shall provide clear attribution and context for each evidence item.
- Evidence items shall be uniquely identifiable and retrievable by stakeholders.
- Where possible, evidence shall be linked to specific commits, versions, or time periods.
- The engineer shall be able to categorize evidence by type and relevance to specific claims or skills.
- Evidence storage shall respect licensing and intellectual property considerations (only sharing what is permissible to share).
